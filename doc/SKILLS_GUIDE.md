# Скиллы (навыки) в Entware Manager: подключение и эксплуатация

> **Версия:** 1.0
> **Дата:** 2026-09-17
> **Статус:** рабочий документ; описывает фактическую конфигурацию проекта
> **Область:** `.opencode/skills/`, `RULES.md` §14, `AGENTS.md`, глобальный `~/.config/opencode/`

---

## 0. Коротко (минимальный рецепт)

```sh
# 1. создать каталог навыка (имя = kebab-case, оно же в frontmatter)
mkdir -p .opencode/skills/ewm-<имя>

# 2. написать .opencode/skills/ewm-<имя>/SKILL.md (шаблон — Приложение A)

# 3. перезапустить opencode и проверить обнаружение
#    в сессии: skill_find query="*"      → навык есть в списке
#              skill_use "ewm_<имя>"     → содержимое загружено в чат
```

Затем — обязательный шаг регламента: добавить строку «задача → навык» в таблицу `RULES.md` §14 (и продублировать в `AGENTS.md`, если это часть рабочего цикла агентов). Без этой строки модель узнаёт о навыке, но **не обязана** его грузить.

---

## 1. Как это устроено: две независимые системы

В проекте одновременно работают два механизма, оба включаются глобальным конфигом `~/.config/opencode/opencode.json`.

| | Ядро opencode (встроенное) | Плагин `@zenobius/opencode-skillful` (v1.2.5) |
|---|---|---|
| Что даёт | блок `<available_skills>` в системном промпте + инструмент `skill` | инструменты `skill_find`, `skill_use`, `skill_resource` |
| Загрузка | по требованию модели, разово (в диалог) | «ленивая»: содержимое подставляется как сообщение пользователя |
| Идентификатор | `name` из frontmatter (`ewm-rdp-client`) | slug из пути: `/` и `-` → `_` (`ewm_rdp_client`) |
| Поиск | по списку из промпта | `skill_find query="..."` (естественный запрос, `*` — все) |
| Ресурсы | — | `skill_resource` (файлы из `references/`, `assets/`, `scripts/`) |

**Кто вызывает навыки.** Автоматики нет: решение принимает модель, увидев список в системном промпте. Обязательность задаётся только регламентом проекта (`RULES.md` §14, `AGENTS.md`) — там 20+ упоминаний навыков.

## 2. Откуда берутся навыки (пути и приоритет)

| Источник | Путь | В проекте сейчас |
|---|---|---|
| Проектные (высший приоритет) | `.opencode/skills/<name>/SKILL.md` | 20 навыков `ewm-*` |
| Глобальные | `~/.config/opencode/skills/<name>/SKILL.md` | `plannotator` |
| Дополнительные каталоги | `skills.paths` в `opencode.json` | 7 навыков `ovi-*` (каталог другого проекта) |
| Встроенные | поставляются с opencode | `customize-opencode` |

Правила:

- при совпадении имён побеждает **более поздний** путь (проект перекрывает глобальные);
- дубликаты логируются и пропускаются;
- обнаружение происходит **при запуске** opencode — после добавления навыка нужен перезапуск;
- внешняя библиотека подключается так (пример из глобального конфига, уже действует):

```json
{
  "skills": {
    "paths": ["/path/to/other-project/.opencode/skills"]
  }
}
```

## 3. Анатомия навыка

```
.opencode/skills/ewm-<имя>/
  SKILL.md          # обязательно: frontmatter + инструкция
  references/       # опционально: подробности, примеры, выдержки
  assets/           # опционально: шаблоны, картинки, конфиги
  scripts/          # опционально: исполняемые скрипты (sh/py/...)
```

Frontmatter (требования спецификации Anthropic Agent Skills):

```yaml
---
name: ewm-<имя>            # ДОЛЖНО совпадать с именем каталога: lowercase, цифры, дефисы
description: Использовать когда ...   # ≥ 20 символов, рекомендуется < 500
---
```

Требования к `description` — это главное, что влияет на срабатывание:

- описывать **когда** применять, а не «что делает»;
- перечислять триггеры: симптомы, имена файлов, команды, типовые формулировки владельца;
- писать в третьем лице (текст попадает в системный промпт).

Тело `SKILL.md`: пошаговый порядок действий, проверяемые команды, готовые фрагменты, чек-лист в конце. Объёмные материалы — в `references/`, чтобы основной файл читался целиком.

## 4. Пошаговое подключение нового навыка

1. **Имя.** Короткое, kebab-case, с префиксом проекта: `ewm-<область>` (например `ewm-telegram`, `ewm-backup`).
2. **Каталог.** `mkdir -p .opencode/skills/ewm-<область>`
3. **`SKILL.md`** по шаблону (Приложение A): frontmatter + инструкция.
4. **Ресурсы (опционально).** `references/` — если инструкция разрастается; `scripts/` — если есть повторяемые команды. Скрипты должны быть безопасны и без секретов.
5. **Проверка обнаружения** (после перезапуска opencode), в сессии:
   - `skill_find query="*"` — навык виден в общем списке;
   - `skill_find query="<ключевые слова>"` — находится по описанию;
   - `skill_use "ewm_<область>"` — содержимое попадает в чат (проверить, что подставилось целиком).
6. **Регистрация в регламенте.** Добавить строку в таблицу `RULES.md` §14:

   ```
   | Правки <область> (<файлы>) | `ewm-<область>` (<что важно: пути, проверки>) |
   ```

   Плюс, если навык участвует в рабочем цикле агентов, — строку в таблицу «Доступные агенты»/чеклист §14.1 в `AGENTS.md` (и/или в промпт конкретного сабагента: `.opencode/agents/<agent>.md`).
7. **Проверка практикой.** Прогнать реальную задачу из новой области и убедиться, что модель действительно загрузила навык до правок (в сессии видно вызов `skill`).

## 5. Как гарантировать, что навык будет загружен

Автозагрузки нет, работают три способа (по убыванию надёжности):

1. **Таблица в правилах** (`RULES.md` §14 + `AGENTS.md`) — основной механизм проекта.
2. **Прямая строка в промпте сабагента** (`.opencode/agents/<agent>.md`): «перед правками X загрузи навык `ewm-<область>` через tool `skill`». Сейчас так сделано только в `ewm-router` и `ewm-tester`.
3. **Явная команда владельца** («загрузи навык …»).

Практика: формулировка в таблице должна совпадать с реальными файлами/словами задачи. Если навык не срабатывает — в первую очередь править `description` (добавить имена файлов и симптомы), а не промпт.

### 5.1 Семантика `skill_find` (как искать и почему «0 совпадений»)

Проверено экспериментально на этом проекте (21 навык):

| Правило | Детали |
|---|---|
| Полный список | `skill_find("*")` — единственный надёжный способ увидеть все навыки (в `debug`: `discovered / parsed / rejected`) |
| Запрос — **одна строка** | ищутся **слова из `description`** (frontmatter), а не из тела `SKILL.md` |
| Логика | **AND по словам в пределах одного описания**: `"NOC консоль ES5"` → `ewm_noc_console` |
| Неизвестное слово | обнуляет весь запрос: `"микрофон audin"` → 0, пока слова `audin` нет ни в одном описании |
| **Массив** запросов | баг плагина: ищет литеральный JSON-текст (`Searching for: "[...]"`) → всегда 0. Передавать только строку |

Следствие: термин, по которому навык **должен** находиться, надо явно добавить в `description` (например, `audin` в `ewm-rdp-client`). Правка описания подхватывается **только после перезапуска** — индекс собирается на старте. Ядровый `skill` (загрузка по имени) индекс не использует и работает всегда.

## 6. Диагностика: «навык не появился»

| Симптом | Причина | Что делать |
|---|---|---|
| Навыка нет в `skill_find query="*"` | не тот каталог (не `.opencode/skills/`) | перенести в правильный путь |
| | нет перезапуска opencode | перезапустить (обнаружение — на старте) |
| | нет frontmatter или `name` ≠ имя каталога | выровнять имя |
| | `description` короче 20 символов | дополнить |
| Навык есть, но не находится поиском | бедный `description` | добавить ключевые слова/симптомы |
| Навык перекрыт другим | дубликат имени (побеждает последний путь) | переименовать или убрать дубль |
| Инструкция «не дочитана» моделью | слишком большой `SKILL.md` | вынести детали в `references/` |
| В логах `[SkillRegistryController] No skills found` | базовые пути пусты / нет доступа | проверить каталоги и права |

## 7. Версионирование `.opencode/` (в этом репозитории — нет)

**Факт.** Корневой `.gitignore` (строка 50) игнорирует `.opencode/` целиком, поэтому локальные правила дополнительно описаны в `.opencode/.gitignore` (там исключены `node_modules`, `package.json`, `package-lock.json`, `bun.lock`, `vibeguard.config.json`). Следствие: **навыки и агенты не версионируются** — при клоне репозитория их не будет.

Если решите версионировать (рекомендация, но не текущее состояние):

1. Убрать из корневого `.gitignore` строку `.opencode/` (сейчас она там не одна — проверить, что рядом нет `!`-исключений).
2. Добавить точечные правила:

   ```gitignore
   # локальная обвязка opencode
   .opencode/node_modules/
   .opencode/package.json
   .opencode/package-lock.json
   .opencode/bun.lock
   .opencode/vibeguard.config.json
   .opencode/plans/
   .opencode/.gitignore
   # навыки и агенты — в репозиторий
   !.opencode/skills/
   !.opencode/agents/
   ```

   (порядок и `!`-исключения зависят от того, что именно перекрывает каталог; проверять `git check-ignore -v <файл>`)
3. **Перед коммитом — `ewm-sec`**: навыки/агенты легко «притаскивают» секреты (пароли, IP, токены) из примеров. Правило проекта: скилл не содержит секретов, только плейсхолдеры вида `<router-host>`.
4. Помнить, что `vibeguard` маскирует секреты только в выводе инструментов — в git он ничего не защищает.

---

## 8. Безопасность

- Никаких секретов в `SKILL.md`, `references/`, `scripts/` — только плейсхолдеры.
- Навыки бывают «чужие» (внешние библиотеки через `skills.paths`): загрузка показывает содержимое и инвентарь скриптов, но не исполняет их автоматически; запускать только осознанно.
- Поле `allowed-tools` в frontmatter — информационное, реальные права ограничиваются уровнем агента (`permission: edit: deny` и т.п. в `.opencode/agents/*.md`).
